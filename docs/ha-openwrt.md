# 节点同步与 OpenWrt DMZ 主备

FireGateway 的规则由两台网关直接复制。OpenWrt 仅通过已有的 ubus / rpcd UCI API 修改现有 DMZ/DNAT 规则的目的 IP；不安装 FireGateway 插件、脚本或工具，不在路由器存放规则快照、心跳或租约。

本版支持一对节点，两台机器角色对称，任意时刻只有一个**主节点**：

- 主节点保存共享规则，并让路由器指向自己；另一台是**备用节点**，同步规则、绑好监听随时待命。
- 主节点掉线或无法转发时，备用节点自动接管，成为新的主节点。原主机恢复后自动跟随新主节点、成为备用，不抢回入口；此后它同样可以接管。
- 任意节点上点击“切换到本机”或“切换到对端”即可手动换主，无需分步移交。

两节点之间没有第三方仲裁，不提供网络分区下的共识选举或硬件隔离；分区时的行为见“故障与恢复”。

## 存储和同步

| 位置 | 内容 |
| --- | --- |
| 节点 `config.json` | 节点身份、对端连接、路由凭据、本机地址覆盖 |
| 节点 `rulesFile`，默认 `rules.json` | 已提交共享规则的可读快照 |
| 同目录 `<rulesFile>.ha.json` | 带校验的权威复制检查点：已提交快照、待决事务、写入授权及最近请求结果 |
| 同目录 `<rulesFile>.ha.json.lock` | 本机进程锁；进程退出后操作系统释放 |
| 同目录 `<rulesFile>.ha.json.archive-*` | 接管、跟随、重新同步等操作前归档的旧状态，供核对和导出规则 |
| 上游防火墙现有 redirect | 原有转发配置及当前目的 IP |

正常保存经过主节点持久化候选、对端 prepare 落盘、对端 commit 落盘、主节点完成落盘，才返回同步成功。检查点用原子替换保存，`rules.json` 是它的派生视图；两文件之间崩溃后从检查点恢复。不要手工编辑集群规则缓存或删除检查点。

变化即时发送；默认每 2 秒交换轻量版本摘要。重试沿用事务 ID。快照上限 256 KiB，普通请求结果保留最近 128 个；旧请求仍需通过预期版本检查。接管时不采用只 prepare、尚未 commit 的候选快照。

请求超时可能意味着对端已经提交。API 返回 `sync_pending` 和可查询的更新标识，后台重试确认；不能把它理解为“修改未发生”。同步成功表示两台节点持久化，不表示备用监听或目标应用已就绪。

## 节点配置

在两台网关分别打开 **设置 → 主备集群 → 节点连接配置**，启用节点同步并填写表单，无需手工编辑配置文件：

1. 填写本机节点 ID、集群 ID、对端节点 ID 和初始主节点 ID。两边的集群 ID、初始主节点保持一致，本机和对端 ID 互换。
2. 填写两台机器的 LAN IPv4、节点专用端口（默认 9091，两边相同）和相同的随机共享密钥。
3. 填写 OpenWrt 的 ubus 地址、账号、密码、已有受管转发配置段名称及故障等待时间。
4. 保存后按页面提示重启两台节点。也可在对端启动后点击“测试已保存的对端连接”，验证地址、端口、共享密钥和身份；测试不会配对、同步规则或操作路由器。
5. 在初始主节点点击“以本机规则配对节点”，再检查同步和监听准备状态。

保存配置仅写入本机，当前连接和流量角色继续使用原配置；页面明确显示“重启后生效”。密码与共享密钥不会回显，留空保留已保存的值。启用后的节点身份和初始主节点不可通过连接表单更换；地址、端口、凭据、路由器 CA 和时间参数仍可修改并在重启后生效。更换共享密钥时同步修改两台节点。

首次从单机启用时，重启会保留并迁移当前单机规则，无需另建规则文件；已有集群规则和检查点不会被重标记为另一个集群。B 应为空或与 A 规则一致。

两台机器固定 LAN IP。节点之间的复制、心跳和接管探测走独立的**节点专用端口**（`cluster.peerPort`，默认 9091，监听在本机 `cluster.address` 上），不经过管理 API、登录会话或反向代理：

- 链路使用双向 TLS 1.3。两台节点用相同的 `peerToken` 和集群 ID 推导出同一个私有 CA，各自签发写有本机节点 ID 的证书；只接受该 CA 签发、且写着配置中对端 ID 的证书。共享密钥本身从不在网络上传输，也无需管理证书文件。
- 由于中间没有代理，端口上的任何 HTTP 应答都来自对端 FireGateway 本身。连接不上、被拒绝或超时才算“对端掉线”；握手被拒或应答异常说明对端在线但配置不一致（密钥、节点 ID、版本），显示为错误，**永远不会触发接管**。
- 防火墙只需允许两台网关之间互访该端口；它不应暴露给其他主机。端口须与管理端口不同。

节点专用密钥、用户登录、OpenWrt 登录分别使用独立凭据。

也可手工配置。A 的示例字段合入它自己的 `config.json`：

```json
{
  "api": { "enabled": true, "host": "192.168.1.10", "port": 9090 },
  "rulesFile": "dmz-rules.json",
  "node": {
    "id": "gateway-a",
    "ruleOverrides": {
      "web": { "localHost": "192.168.1.10", "targetHost": "127.0.0.1", "targetPort": 3000 }
    }
  },
  "cluster": {
    "id": "dmz",
    "initialWriter": "gateway-a",
    "peerId": "gateway-b",
    "peerPort": 9091,
    "peerToken": "replace-with-the-same-random-token-of-at-least-32-characters",
    "address": "192.168.1.10",
    "peerAddress": "192.168.1.11",
    "routerUrl": "https://192.168.1.1/ubus",
    "username": "existing-router-api-user",
    "password": "replace-with-router-password",
    "caFile": "/etc/firegateway/router-ca.pem",
    "redirects": ["firegateway_dmz"],
    "pollInterval": 2,
    "failoverAfter": 10
  }
}
```

B 使用同一集群 ID、初始写入者、节点端口、随机 token、上游地址及受管 redirect；修改以下字段：

| 字段 | B 的值 |
| --- | --- |
| `api.host` | `192.168.1.11` |
| `node.id` | `gateway-b` |
| `cluster.peerId` | `gateway-a` |
| `cluster.address` | `192.168.1.11` |
| `cluster.peerAddress` | `192.168.1.10` |
| `node.ruleOverrides.web.localHost` | `192.168.1.11` |
| `node.ruleOverrides.web.targetPort` | `4000`，若 B 上服务端口不同 |

`peerToken` 应由安全随机数生成器生成，不使用示例文本。连接设置、节点身份和文件路径修改需要重启；本机规则覆盖可在设置页面直接修改。

共享入口监听端口在两机保持一致，上游只切换目的 IP。目标服务可以使用不同的本机端口。服务进程、业务数据和连接状态不会随规则复制。

## 节点如何与 OpenWrt 协作

一句话：**OpenWrt 上那条 DNAT 规则的 `dest_ip` 指向谁，谁就转发流量；主节点负责让它指向自己。** 路由器是唯一的流量仲裁者；FireGateway 不在路由器上存放任何状态，只做两件事——每 `pollInterval` 秒读一次受管 redirect，必要时由主节点改一次 `dest_ip`。

```text
        外网连接
           │
   ┌───────▼────────┐  firewall.firegateway_dmz
   │    OpenWrt     │  target=DNAT  dest_ip=192.168.1.10
   └───┬────────┬───┘
       │        │      新连接只会送到 dest_ip
       ▼        ▼
  ┌────────┐  ┌────────┐
  │ A .10  │◄─►│ B .11  │  节点专用端口 9091（双向 TLS）：
  │主·门开 │  │备·门关 │  规则复制、心跳、就绪状态
  └────────┘  └────────┘
```

**两台节点始终做的事：**

1. **准备监听。** 每次规则提交或同步后，两台节点都把所有启用规则的端口绑定好，但新连接要经过“转发门”。门关着时，连接被接受后立即关闭，不会转发。一条规则绑定失败只报告这一条，其余规则照常就绪。全部绑定成功即为“就绪”，并通过心跳告诉对端。
2. **读路由器、跟随它开关门。** 读到 `dest_ip` 等于本机地址就开门（状态页显示“正在转发”），等于对端就关门。关门只拒绝新连接，已建立的连接自然结束——路由器已经把新连接送往别处，强行切断旧连接没有收益。
3. **路由器 API 暂时读不到时保持现状。** 状态显示“路由器不可读”，两台节点都按上一次读到的角色继续工作。规则复制不依赖路由器，也照常进行。

**只有主节点会修改路由器，且只在它需要“认领”入口时：** 刚配对、刚接管或刚经切换成为主节点。认领完成（路由器指向本机）后便不再操作路由器。

**备用节点在以下情况接管，成为新主节点：**

- 主节点**掉线**：节点端口连不上持续 `failoverAfter` 秒，接管前再直接探测一次确认；或
- 主节点**在线但无法转发**：它已持有相同规则却报告未就绪（例如端口被占用、地址覆盖错误），持续 `failoverAfter` 秒；

并且备用节点自己已就绪。接管时它先在本机进入新的写入代次（epoch+1），从此拒绝原主机迟到的规则提交，然后认领入口：

1. 用缓存的只读会话读出受管 redirect，确认和刚才观测的一致；
2. 新建一个独立的暂存会话，确认它没有待提交改动，只 `uci.set` 受管 redirect 的 `dest_ip`；
3. 再读一次已提交配置，确认期间没有别人改过；
4. `uci.apply`（`rollback: true, timeout: 30`）——OpenWrt 应用新防火墙配置并启动 30 秒回滚计时；
5. 读回确认 `dest_ip` 已是本机，再 `uci.confirm` 取消回滚。

任一步在 apply 之前失败，就 `uci.revert` 丢弃暂存，路由器保持原状，下一轮再试。apply 之后出错（超时、读回不符、confirm 失败）结果未知，状态页显示“切换中”：此后不急于重复操作，等回滚窗口（约 35 秒）过去再看路由器——

- 指向本机：没有回滚，认领完成。期间读到指向本机就已经开门转发。
- 仍指向对端：OpenWrt 已回滚，再试一次。连续 3 次结果未知仍未成功就停下并报错，需检查路由器后在页面上重新切换。

节点重启后若发现路由器已经指向自己而认领尚未完成，也会等一个回滚窗口再确认，防止重启前那次未确认的切换随后被回滚。

**为什么不会来回切换：** 只有备用节点会接管，且接管后它就是主节点；原主机在失联期间仍以为自己是主节点，但它的认领早已完成，不会再动路由器。恢复联系后它发现对端处于更新的代次，自动跟随成为备用。

**手动修改路由器也能收敛：** 若有人在 LuCI 中把 `dest_ip` 改到了备用节点，且两节点规则一致，主节点会把主节点身份移交给正在接收流量的那台，而不是把入口抢回来。

## 手动切换

状态页的主操作只有一个按钮：本机是备用时显示“切换到本机”，本机是主节点时显示“切换到对端”。两台节点上都能操作，效果相同：

1. 确认对端在线、两边规则一致且无进行中的同步，目标节点已就绪；
2. 先把主节点身份（共享规则写入权）移交给目标节点；
3. 新主节点随即认领入口，流程同上一节。

第 2 步之后即使第 3 步失败，也只有一个主节点，它会持续尝试认领。已建立的连接留在原节点上自然结束，新连接进入新主节点；旧 TCP 连接需要重连。

计划内维护或在线升级（OTA）某台节点前，先把主节点切到另一台，维护完成后按需切回。

## OpenWrt 条件

设备需已提供 ubus HTTP API，账号具有所需原生方法权限：`uci.get`、`uci.changes`、`uci.set`、`uci.apply`、`uci.confirm`、`uci.revert`。权限或方法缺失时显示错误，不自动安装组件或开放更大权限。

受管 redirect 必须已存在、启用、有稳定名称、`target=DNAT`，目的 IP 属于这对网关。不能使用 `@redirect[0]`。在路由器原管理界面创建并检查入口规则，例如现有全端口 DMZ 规则的 UCI 内容可以是：

```uci
config redirect 'firegateway_dmz'
    option name 'FireGateway DMZ'
    option src 'wan'
    option dest 'lan'
    option proto 'tcp udp'
    option target 'DNAT'
    option dest_ip '192.168.1.10'
```

也可管理已有的指定端口转发，无需配置全端口 DMZ。程序仅修改明确列出的 `dest_ip`，流程见上一节。日常轮询复用同一个读会话，每次切换只额外创建一个暂存会话。不执行远程 shell，不清空连接跟踪。

OpenWrt 的 apply 会触发配置变更事件；成功响应与读回证明配置已提交，**不能证明内核防火墙已重载成功或外部流量已经可达**。必须在目标设备上演练入口新连接。UCI 读后写也不是原子条件更新：受管入口应由单一控制器管理，切换期间避免 LuCI 或其他工具并发编辑防火墙。

## 首次启动

1. 停止旧版路由器插件控制器，导出已确认的共享规则。不要让两套入口控制器同时工作。
2. 通过 Web 表单给两节点配置参数，各自保存到本机的 `rulesFile`。已有单机规则在启用时保留；A 也可以携带旧 `forward`，首次启动自动迁移。B 保持规则为空，或与 A 完全一致。已有集群缓存不能直接作为新集群权威数据。
3. 启动两节点并分别设置管理账号。在 A 的设置 → 主备集群点击“以本机规则配对节点”。此操作不联系路由器。配对后两节点共用主节点的账号、租户和 API token：A 的管理账号自动迁入共享账号，B 配对前设置的本机账号随之失效，之后在任一节点登录均使用同一组账号。
4. 通过规则页面导入或维护规则，设置各节点本机覆盖。共享规则由主节点保存，在备用节点上的编辑会自动交给主节点。
5. 确认两节点规则已落盘、本机及对端均就绪、上游目标指向 A。绑定失败的规则会在状态中列出，其余规则照常转发。

空对端的第一次配对由其配置中的 `initialWriter` 和专用凭据授权；已有不一致的本地规则不会被静默覆盖。需要覆盖时先导出，再使用有明确归档确认的“以对端为准重新同步”。

## 从旧版本升级

节点链路协议升级到 4，旧版与新版节点互相不认（显示“配置错误”，不会触发接管），请两台一起升级。旧版的“冻结”“已接管”等状态不再使用，升级后自动收敛：若旧版接管后入口在 B、写入者仍是 A，A 会把主节点身份移交给 B；旧版处于冻结只读状态的节点会自动跟随对端。

## 故障与恢复

- **主节点整机掉线：** 备用节点连续无法连接节点端口达到 `failoverAfter`（默认 10 秒），再直接探测一次，随后成为新主节点并切换入口。密钥、身份或版本不一致只显示错误，不计为掉线。实际恢复时间还要加上探测、OpenWrt apply 及下一轮观测。
- **主节点在线但无法转发：** 它报告未就绪持续 `failoverAfter`，且备用节点已就绪，备用节点同样接管。原主机仍转发其余正常规则，直到入口切走。
- **接管后、原主机恢复前：** 新主节点可以直接修改规则，保存结果标记为“仅本机保存”（`local_only`）。此时只有一份副本。
- **原主机恢复：** 它归档未完成的事务，自动采用新主节点的规则，成为备用节点，两边随即回到“已同步”。不需要任何手动操作；需要时再“切换到本机”。
- **切换结果未知：** 无需手动操作，见“节点如何与 OpenWrt 协作”。若停在“切换中”并报错，检查路由器和节点链路后重新点击切换。
- **路由器 API 不可用：** 两台节点保持最后一次观测到的角色继续转发，规则复制照常。此时无法接管——备用节点没有办法修改入口。
- **对端长期停机、本机是主节点但需要改规则：** 对端离线时主节点的共享规则默认只读（不确定对端是真的停机还是只是链路断开）。在“高级”中点击“允许单机修改”，确认对端确实已停机后，进入“仅本机保存”模式；对端回来后自动同步。
- **两台节点都单独修改过规则（冲突）：** 只会在节点互联中断、两边都“允许单机修改”或接管后发生。程序不会自动合并，状态页显示“冲突”。在要放弃修改的那台节点上点击“以对端为准重新同步”：本机规则先归档，再采用对端规则。需要保留的修改可从归档文件找回后重新录入。
- **在线升级（OTA）或重启：** 升级主节点前先把主节点切到另一台，或临时调大 `failoverAfter`。否则停机超过 `failoverAfter` 时对端会接管，之后按需切回。

两节点互联中断也可能触发备用节点接管；没有第三方仲裁，不能仅靠探测消除误判。若原主机实际仍在运行，路由器切换后新连接全部到新主节点，原主机只处理已建立连接，不会出现两边同时接收新连接；原主机在失联期间保持共享规则只读，恢复联系后自动跟随，因此不会出现两份各自宣称同步成功的配置。已有 TCP 连接需要重连，旧 UDP NAT 映射可能等待设备超时，不保证无损切换。

已知限制：若有人手动把路由器指向一台已离线的备用节点，没有节点会自动纠正。在主节点上点击“切换到本机”，或在路由器上改回即可。

## 检查与备份

`GET /api/cluster` 查看主备角色、是否在转发、同步状态、两节点准备状态、入口状态及问题列表。`GET /ready` 仅在本机转发门打开（入口指向本机）时返回 200，不验证目标应用健康。

备份各节点的 `config.json`、`rulesFile` 和 `.ha.json` 检查点。运行中复制这些文件不等于取得一致性备份；建议停机备份，或通过 `GET /api/cluster/snapshot` 导出已提交共享规则。归档文件用于审计、比较与提取规则，不应直接覆盖正在运行的检查点。
