# 节点直连同步与非侵入式上游切换

状态：节点直连方案已实现，部署及实际接口以 [部署说明](ha-openwrt.md) 和 [API 文档](api.md) 为准。本文保留设计目标及协议边界。持久化采用单个原子检查点和派生规则快照；恢复后通过受控配置移交解除只读，回切后提供显式重新启用自动接管。

## 目标与边界

首先实现两台 FireGateway 的主备：A 承载流量，B 提前准备，A 整机掉线后 B 修改上游已有的 DMZ/DNAT 转发目标接管。规则由 A、B 直接同步；本机 IP、目标服务覆盖和凭据保留在各自节点。

OpenWrt 仅作为上游设备，通过它已有的管理 API 读取和修改指定转发规则。不安装 FireGateway 插件、脚本、守护进程或 conntrack 工具，不存放共享规则、心跳、锁、租约、任期或集群元数据。已有 API 未开放或权限不足时报告能力不足，由管理员配置现有管理接口；程序不自动安装组件或扩大权限。

两节点没有独立仲裁，心跳超时不能证明对方已关机。因此本版分开管理流量角色与配置写入角色：允许指定备用节点自动接管入口，但不因心跳超时自动产生第二个配置写入者。默认不自动回切，不把 UCI 的目的 IP 当作分布式锁。

## 拓扑与职责

```mermaid
flowchart LR
    A[网关 A：配置写入者 / 初始流量主机] <-->|认证的节点 API：规则、确认、心跳| B[网关 B：规则副本 / 备用机]
    R[OpenWrt 或其他上游路由器] -->|已有 DMZ / DNAT| A
    B -.->|故障时通过已有 API 修改目的 IP| R
```

- `RuleReplicator`：规则版本、持久化、节点复制、重试、恢复；不依赖路由器客户端。
- `PeerMonitor`：对端身份、心跳、持久化版本、监听准备版本和失联状态。
- `FailoverController`：判定是否具备接管条件，调用上游适配器，控制本机转发。
- `UpstreamAdapter`：能力检查、读取指定入口、修改目标、应用并读回。没有规则发布和主备选举接口。

初版明确只有一对节点、一个指定自动接管者。多备用节点的候选竞争另行设计，不能靠随机延迟或修改 IP 来模拟多数派选举。

## 存储

| 数据 | 存放位置 | 同步方式 |
| --- | --- | --- |
| 共享转发规则 | A、B 的 `rules.json` | 节点之间传输版本化快照 |
| 复制日志、待决写入、确认状态 | 各节点数据目录 | 协议交换状态，不直接复制文件 |
| 配对身份、配置写入者、授权代次 | 各节点数据目录 | 配对或受控角色移交时确认并持久化 |
| 节点 ID、本机绑定与服务覆盖 | 各节点 `config.json` | 不同步 |
| 路由器地址、登录凭据、节点通信密钥 | 各节点私有配置 | 不进入共享规则 |
| DNAT/DMZ 的目标 IP | 上游原有防火墙规则 | 仅入口切换时通过现有 API 修改 |

保留 `forward` 到独立规则文件的迁移，以及原有规则导入导出格式。共享规则独立管理，不能通过复制整个 `config.json` 同步。

规则快照增加 `writerEpoch`、`writerId`、`revision`、`parentChecksum`，并保留 `schemaVersion`、`clusterId`、`checksum`、`rules`。`revision` 在一次写入授权代次内单调增加；完整版本用 `(writerEpoch, revision)` 表示。校验值覆盖快照全部内容，计算时排除校验值本身。

每次修改另有稳定的 `updateId`。同一个请求重试不能创建新版本。高版本号本身不是接受条件：还必须验证写入者授权、父版本链和集群身份。禁止按时间戳或“谁版本大”直接覆盖，禁止自动合并两条分叉。

## 正常写入与复制

默认采用单写入者、同步持久化确认，适用于修改频率低的网关规则。初始由 A 写入；在 B 的管理页面保存共享规则时，B 在验证用户权限后将请求交给 A，不在本地另起一条写入链。

1. A 校验请求携带的预期版本，串行生成下一份完整快照，持久化待决记录。此时不替换正在使用的规则。
2. A 向 B 发送 `prepare(updateId, expectedVersion, snapshot)`。B 验证身份、写入授权代次、父版本、规则和校验值，保存候选快照并 `fsync`，返回持久化确认。
3. A 记录提交意图并发送 `commit(updateId)`。B 原子切换到新规则快照，持久化提交状态后返回确认。B 此时可能开始准备监听；持久化成功与监听成功分别报告。
4. A 收到确认后原子切换自己的规则快照并记录完成，才向管理端返回“已保存并同步”。随后按各节点本机覆盖更新运行配置。

快照替换、日志和恢复流程必须保证每个节点的提交状态可在崩溃后恢复，不能依赖两个独立文件恰好同时写成功。可使用带校验的顺序日志和原子快照检查点；回收日志前需保留当前快照、最后确认点与所有待决事务。

这里的成功保证是“两台节点都持久化了此配置”，不代表两个进程在同一时刻应用，也不代表备用服务已经可用。管理界面分别展示“已保存”“已同步”“本机已准备”“对端已准备”。监听冲突不能被一个同步成功标志掩盖。

超时不是“没有生效”。尤其 B 已提交但确认丢失时，A 保留待决状态，按同一 `updateId` 查询或重试，不回滚 B，也不接受下一条可能冲突的修改。API 返回可查询的待确认结果，而不是让用户误以为旧配置绝对未变。重复 `prepare`、`commit` 和查询必须幂等；相同 ID 携带不同内容应拒绝。

## 心跳、补同步和加入

- 正常变化即时推送；每 2 秒交换一次轻量心跳和版本摘要，作为连接检测和丢失通知的补救。没有变化时不传输完整规则。
- 心跳包含节点身份、启动实例 ID、授权代次、持久化版本、监听准备版本、流量角色和待决写入摘要。心跳存活不等于业务健康。
- 断线重连后先核对授权和共同确认点，再重放未完成事务或传输完整快照。首次加入需要明确选定配置源并授权，不能由先启动的机器随机覆盖另一台。
- 节点通信采用受信任的 HTTPS 和专用节点凭据，校验集群 ID、节点 ID、实例会话和协议版本。节点凭据与用户登录、路由器登录分离；拒绝跨节点重定向、超限消息及未配对节点。
- 监听准备失败只使该节点失去接管资格；共享配置仍可查看和复制，本机覆盖仍可修复。
- 对端不可达时保留已提交规则并继续现有流量服务；默认暂停共享配置写入。本机覆盖仍可修改，但修改后重新计算接管就绪状态。

快照大小保留上限并在节点协议中校验，不再称为“路由器限制”。不引入文件系统目录复制，也不定时推送凭据、日志或应用数据。

## 本机绑定与服务覆盖

沿用按规则 ID 设置的 `node.ruleOverrides`，应用顺序为“共享规则 + 本节点覆盖”。例如，共享入口是 TCP 8080：

| 节点 | `localHost` | `targetHost` | `targetPort` |
| --- | --- | --- | --- |
| A | `192.168.1.10` | `127.0.0.1` | `3000` |
| B | `192.168.1.11` | `127.0.0.1` | `4000` |

修改本机覆盖不改变共享规则版本。两节点入口端口保持一致，因为本版只切换上游目的 IP；不同服务端口用目标端口覆盖。接管前验证目标 LAN IP 属于本机、监听地址可接收该 IP 的流量、所有启用端口已绑定。服务进程与业务数据需在备用节点另行准备，本功能不复制应用数据或连接状态。

## A 整机掉线后的接管

建议默认心跳间隔 2 秒，连续失联达到 10 秒后进入故障怀疑状态；另对 A 的管理地址直接探测并复查上游当前目标。额外探测能减少误切换，不能消除网络分区的不确定性。探测结果为认证失败或配置不兼容时应报告配置错误，不能直接当成整机死亡。

1. B 必须已完成配对、拥有可恢复的已提交规则，并能准备全部启用的监听。只有候选快照而没有已提交快照时不能接管。
2. B 持久化“准备接管”状态，暂停接收 A 的新规则提交，避免延迟请求在角色切换期间改变接管快照。
3. 确认上游指定入口仍指向 A；若指向未知地址、多个入口目标不一致或存在外部修改，停止自动操作并显示具体原因。
4. B 只修改指定入口的目标 IP，调用设备已有的应用接口，再读回确认。超时进入 `switch_pending`，先重新读取结果，不能盲目反复切换或覆盖外部变更。
5. 在应用成功、配置读回匹配、本机仍准备就绪后开放 B 的转发；没有成功确认时保持关闭。持久化已接管状态，进程重启后也不能自动回到抢占模式。
6. A 恢复后先读取本机持久化状态、对端状态及上游目标。若入口已在 B，A 保持备用，禁止写回自己的 IP。恢复复制关系并处理待决记录后再准备为备用。

B 接管时使用最新已提交快照。A 已向用户返回同步成功的版本必须在 B 上存在。只有 `prepare` 的记录不算提交；B 已执行 `commit` 但客户端未获回复的版本可能被使用，这属于结果未确认的写入，必须能通过 `updateId` 查询。

接管期间 A 迟到的复制请求必须被拒绝。重新建立复制会话前核对双方状态，旧会话和旧授权代次不能继续写入。分歧快照先归档，不自动用旧主的本地内容覆盖接管节点。

默认自动切换方向为 A → B，接管后保持 B；不让两个节点在互相失联时轮流改目的 IP。恢复后的回切或重新设定备用方向走受控移交流程。持续承受多个先后故障的自动候选切换不在初版范围内。

## 配置写入角色的移交

自动流量接管不自动赋予 B 独立配置写入权限。这是两节点、无外部仲裁下选定的默认行为，保证网络隔离时不会产生两份各自宣称保存成功的配置。

- 两节点都在线：先冻结 A 的共享规则写入，处理待决事务并核对同一提交点，双方持久化对 B 的新授权代次，才开放 B 写入。移交中断时保持只读并恢复握手。流量无需为配置角色移交而回切。
- A 持续离线：B 自动承载流量，默认共享规则只读。若需立即在 B 修改共享规则，管理员需先确认 A 已停机或已隔离写入能力，再执行强制配置角色提升。该操作记录新授权代次与审计事件。
- 强制提升后只有一份可用副本：明确进入降级写入模式，返回“仅本机保存”，不能继续显示“两节点同步成功”。旧主回归后必须重新授权加入并核对、归档旧状态。

只提高 epoch、增加探测次数或读回路由器 IP，都不能替代对旧写入者的隔离。若以后要求任意网络分区下仍能自动产生唯一可写主节点，需要第三个仲裁参与者；当前方案不偷偷将这项职责塞回 OpenWrt。

## OpenWrt 适配方式

利用设备已有的 ubus HTTP / rpcd UCI 能力，建立专用会话，发现支持的方法，再读取明确指定的稳定命名 redirect。仅接受启用的 DNAT 规则；修改字段限制为 `dest_ip`，不自动创建全端口暴露规则。

优先使用现有 UCI 暂存、应用、确认机制（设备支持时使用 `uci.set`、`uci.apply`、`uci.confirm`），具体参数和成功语义按能力检测及目标 OpenWrt 版本验证。应用接口不足时报告不支持自动切换，不回退到安装自定义插件或远程 shell。其他路由器实现相同适配器职责。

使用独立会话，检查该会话的待提交变更，只暂存本次指定修改；切换前后核对受管入口指纹，保留其他字段及不相关规则。不能把 UCI 读后写称为原子 compare-and-swap：设备现有 API 未提供原子条件写时，外部管理员与控制器并发修改仍有竞争，需要对这些入口约定单一管理者。

读回 `dest_ip` 只能确认配置，不能证明所有内核流量路径已切换。还需验证设备的应用/重载完成状态；实机验收应从上游入口测试新连接。没有现成的安全连接跟踪管理接口时不主动清理 NAT 状态，旧 TCP 连接需要重连，旧 UDP 映射可能等待设备超时。不得宣称连接无损迁移。

规则复制无需调用上游 API，上游管理接口短时故障不会阻断节点间同步。入口状态监测与复制状态分别展示。转发门通过对端协商状态和最近的上游观测控制；观测超过配置的有效期后关闭，避免永久沿用旧入口判断。此机制缩短旧节点继续处理流量的窗口，不是租约或硬隔离，不能保证网络分区下现存连接绝无短暂重叠。

## 管理接口与界面变化

节点内部新增版本化、独立认证的心跳、准备、提交、事务查询、快照获取接口。用户规则 CRUD 继续使用现有 API；请求增加预期版本和幂等标识，备用节点代理时保留这两个字段及授权上下文。

`GET /api/cluster` 分别返回 `trafficRole`、`configRole`、`peerState`、`replicationState`、`localVersion`、`peerDurableVersion`、`localPreparedVersion`、`peerPreparedVersion`、`pendingUpdateId`、`upstreamState` 和错误。不能再用单个 `active/standby` 或 `appliedRevision` 暗示所有状态一致。

移除“初始化路由器集群”，替换为“配对节点 / 选择初始配置源”。提供受控角色移交、待决事务查询及冲突快照导出；强制配置提升单独展示失去双副本确认的影响。本机地址覆盖界面保留。

## 替换旧实现

1. 保留 `internal/config/rules.go` 的规则分离、校验、迁移与原子文件基础，改造为可恢复的节点复制事务。
2. 将 `internal/ha/controller.go` 中的规则发布与流量切换拆开。删除对路由器 `publish/status/claim/release` 和路由器租约的依赖。
3. 将 `internal/ha/client.go` 改为内置 OpenWrt API 适配器，新增节点协议客户端与服务端。入口切换只通过适配器执行。
4. 移除 `cmd/firegateway-router`、路由器自定义 ACL/配置部署文件、插件构建目标与安装流程；同步更新 API 文档及前端文案。
5. 已部署旧方案的迁移需先停止旧控制器，导出已确认的权威规则，选定初始节点并完成配对，确认备用已同步和准备，再启用新切换机制。不能两套控制器同时运行，也不能直接把任意旧缓存升级成权威配置。

## 验收条件

| 场景 | 必须满足的结果 |
| --- | --- |
| A 修改共享规则 | B 持久化确认后才返回同步成功；不同本机覆盖均保持不变 |
| B 修改共享规则 | 请求交给唯一配置写入者；并发过期版本返回冲突 |
| 重复、乱序、伪造节点请求 | 幂等或拒绝，不产生额外版本，不接受其他节点身份 |
| 每个 prepare/commit/ACK 边界断线、掉电 | 不丢失已确认规则；未确认结果可查询，不能悄悄当成已回滚 |
| A 整机断电 | B 用已提交规则准备监听，调用原生 API 切换入口；不访问自定义路由器方法 |
| A 恢复、旧消息延迟到达 | A 不抢回入口，不覆盖 B；旧复制会话被拒绝 |
| 仅节点互联故障 | 不产生双配置写入者，不发生双向反复切换；明确报告隔离状态 |
| 备用本机 IP 错误或端口冲突 | 同步状态与准备失败分别可见，B 不接管 |
| 路由 API 超时、重载失败、规则被人工改动 | 可恢复地报告状态，不盲目覆盖、不虚报切换成功 |
| 路由管理 API 故障 | 节点规则同步仍可工作；入口监测按自己的策略处理 |
| OpenWrt 标准 API 实机演练 | 无新增插件、脚本、工具包或集群文件；验证新 TCP/UDP 流量与旧 NAT 映射行为 |

自动化测试覆盖节点协议、故障恢复、管理 API 和原生 UCI 调用；最后一项 OpenWrt 实机演练仍需在目标设备执行。OpenWrt 原生 apply 的成功响应不能单独证明内核重载及外部流量成功。
